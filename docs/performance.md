# 성능 측정 보고서

`ui-drift` 의 충돌/압축, 이벤트 복사, 렌더링 경로를 **측정**하고, 측정으로 확인된 병목만 개선했다.
추측만으로 넣은 최적화는 없다. 이 문서의 수치는 `npm run bench:core`, `npm run bench:editor` 로 다시 만들 수 있다.

## 1. 측정 환경과 방법

| 항목 | 값 |
| --- | --- |
| CPU / OS | Intel(R) Core(TM) i7-8565U CPU @ 1.80GHz ×8 (노트북), win32 10.0.26200 |
| Node.js | v24.20.0 |
| 브라우저 | Playwright Chromium 156.0.8078.4 (headless, 뷰포트 1280x900) |
| 컬럼 수 | 12 |
| 항목 수 | core: 100, 300, 1000, 2000 / 에디터: 100, 300, 1000 |

* **core(`scripts/bench-core.mjs`)**: 빌드 산출물 `dist/core.js` 를 Node 에서 실행. DOM 과 무관한 순수 계산 비용. 각 케이스를 한 번 실행해 시간을 가늠한 뒤 반복해 중앙값(ms)을 기록한다(순수 함수이므로 매 반복 입력이 같다). 한 번이 15000ms 를 넘으면 그 이상의 n 은 건너뛴다.
* **에디터(`scripts/bench-editor.cjs`)**: **실제 Chromium** 에서 각 연산을 9회 실행한 중앙값. 연산 직후 `offsetHeight` 로 스타일/레이아웃을 강제해 DOM 반영 비용까지 포함한다. 전체 벤치를 3회 반복해 항목별 중앙값을 쓰고 괄호에 반복 간 최소~최대를 적었다. 레이아웃은 12열, 3x2 항목을 4개씩 쌓은 빽빽한 배치이며 title/content/props 를 가진다.
* 화살표 앞의 값은 개선 전, 뒤의 굵은 값은 개선 후이다. 개선 전 수치는 같은 스크립트로 개선 전 코드에서 한 번 측정한 값이다(core 는 n=2000 을 시간 한도 때문에 측정하지 않았다).
* **이 수치는 프로그램 호출 경로의 비용이다. 사용자 드래그의 프레임 시간(포인터 이벤트 → 미리보기 → 페인트)이 아니다.** jsdom(Jest) 시간은 성능 지표로 쓰지 않았고 어떤 결과도 jsdom 수치로 해석하지 않았다.
* 노트북 환경이라 실행 간 편차가 크다(에디터 수치는 ±30% 이상 흔들릴 수 있음). 작은 차이(수 ms)는 의미가 없고 자릿수가 바뀐 변화만 유의하다고 본다.

## 2. 병목 분석

| 의심 항목 | 측정 결과 | 조치 |
| --- | --- | --- |
| 항목 수 증가에 따른 충돌 탐색 | `compact` 가 배치된 전체 항목을 선형 탐색 → n 에 대해 제곱 이상으로 증가 | 열별 색인(`ColumnIndex`)으로 같은 열의 항목만 탐색 |
| y 가 큰 항목을 한 행씩 올리는 압축 | `tall` n=1000 압축 **2.5초**, `moveItem` 3.0초 (y 가 클수록 선형 증가 × n) | 위로 올릴 위치를 한 번에 계산(`ceiling`), 충돌 시 아래로 점프 |
| 빈 자리 탐색 | `addItem` 자동 배치가 모든 (행, 열) 후보마다 전체 항목 선형 탐색 | 같은 색인 사용 + 막은 항목의 오른쪽 끝으로 건너뛰기 |
| 변경 없는 전체 항목 DOM 갱신 | `refresh` 가 n=1000 에서 약 1ms. 위치 문자열·콘텐츠 키 캐시가 이미 동작 | **조치 없음** (병목 아님) |
| 내부 이력을 끈 상태의 스냅샷 | 이력 스택은 이전 레이아웃의 **참조**만 쌓는다(항목 복사 없음). 이력 켬/끔 비교(워밍업 후 교대 6회, n=1000): 켬 22.1~26.7ms, 끔 22.4~26.4ms → **차이 없음** | 의미가 명확한 `history:false` 옵션 제공(메모리 보관 제거). 성능 개선 효과는 없음 |
| 이벤트용 복사 | `layoutChange` 마다 `cloneLayout`(n=1000 에서 약 0.8ms) + 변경 비교 | 리스너가 없으면(또는 `emit:false`) 복사·비교를 생략. 변경 감지를 JSON 직렬화 2회에서 구조 비교로 교체 |
| 외부 모델 동기화 시 반복 렌더링/이벤트 | 항목을 하나씩 `updateItem` 하면 항목마다 압축+렌더+이벤트 (n=1000, 20% 변경 시 이벤트 200회, 1916ms) | `syncItems()` 로 최종 상태를 한 번에 반영 (이벤트 1회, 18.8ms) |
| 위치 변경 시 브라우저 비용 | n=1000 의 `moveItem` 약 25ms 중 JS 구간(core 약 4ms + 직렬화/복사/applyItems 합 2ms 미만)을 뺀 나머지는 **속성 변경에 따른 스타일/레이아웃 계산**으로, 실제 위치가 바뀐 항목 수에 비례 | 변경된 항목만 DOM 에 쓰도록 이미 캐시됨. 추가 조치 없음 |

동일 입력의 배치 결과는 유지된다. `test/core/compactEquivalence.test.ts` 가 **개선 전 구현을 그대로 보존한 참조 구현**과 무작위 입력 3000건(겹침 입력, locked, anchor, float, 컬럼 4~12 조합)과 `findFreePosition` 2000건의 결과가 완전히 같음을 검사한다.

읽는 법
* `moveItem 변경 없음` 은 같은 자리로의 이동으로, 압축 계산과 변경 감지 비용이 드러난다.
* `syncItems` 와 `updateItem 개별 호출` 은 같은 변경(전체의 20% 항목의 폭을 번갈아 바꿈)을 반영하며 `layoutChange` 리스너 1개를 둔 상태이다. 이벤트 횟수는 n=100/300/1000 에서 1 대 20 / 1 대 60 / 1 대 200 이다.
* `생성(첫 렌더)` 가 개선 전보다 느려 보이는 것은 노이즈 범위이다(코드 경로가 같고 반복 간 편차가 같은 크기). 첫 렌더 비용은 DOM 요소 생성이 지배한다.

## 5. 남은 한계

* 압축 자체는 항목 수에 대해 여전히 대략 O(n²/컬럼 수) 이다(열별 목록을 선형 스캔). n=2000 의 `compact` 가 15~16ms 수준이라 현재 사용 범위에서는 충분하며, 더 큰 규모가 필요해질 때 열별 정렬 구조로 바꾸는 것을 검토한다.
* 드래그 중 미리보기는 셀이 바뀔 때만 core 를 다시 계산한다(`PointerController`). 포인터 이동 중의 프레임 시간은 이 문서에서 측정하지 않았다.
* `tall` 은 의도적으로 극단적인 입력이다. 일반적인 편집 상태는 `dense`/`mixed` 에 가깝다.

## 6. 재현

```bash
npm run build
npm run bench:core                       # Node, dist/core.js
npx vite --config vite.config.dev.mjs --port 5199 --host 127.0.0.1 &
npm run bench:editor                     # Chromium (BENCH_URL 로 서버 주소 지정)
```

환경 변수: `BENCH_SIZES`(예: `100,300,1000`), `BENCH_BUDGET_MS`, `BENCH_REPEAT`.
