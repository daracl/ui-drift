# 성능 측정 보고서

`ui-drift` 의 충돌/압축, 이벤트 복사, 렌더링 경로를 **측정**하고, 측정으로 확인된 병목만 개선했다.
추측만으로 넣은 최적화는 없다. 이 문서의 수치는 `npm run bench:core`, `npm run bench:editor` 로 다시 만들 수 있다.

## 1. 측정 환경과 방법

| 항목 | 값 |
| --- | --- |
| CPU / OS | Intel(R) Core(TM) i7-8565U CPU @ 1.80GHz ×8 (노트북), win32 10.0.26200 |
| Node.js | v24.20.0 |
| 브라우저 | Playwright Chromium 156.0.8078.4 (headless, 뷰포트 1280x900) |
| 컬럼 수 | 12 |
| 항목 수 | core: 100, 300, 1000, 2000 / 에디터: 100, 300, 1000 |

* **core(`scripts/bench-core.mjs`)**: 빌드 산출물 `dist/core.js` 를 Node 에서 실행. DOM 과 무관한 순수 계산 비용. 각 케이스를 한 번 실행해 시간을 가늠한 뒤 반복해 중앙값(ms)을 기록한다(순수 함수이므로 매 반복 입력이 같다). 한 번이 `BENCH_BUDGET_MS`(기본 20000ms, `scripts/bench-core.mjs`)를 넘으면 반복과 그 이상의 n 을 건너뛴다. (이 문서 초판은 15000ms 라고 적었으나 코드 기본값은 20000ms 다.)
* **에디터(`scripts/bench-editor.cjs`)**: **실제 Chromium** 에서 각 연산을 9회 실행한 중앙값. 연산 직후 `offsetHeight` 로 스타일/레이아웃을 강제해 DOM 반영 비용까지 포함한다. 전체 벤치를 3회 반복해 항목별 중앙값을 쓰고 괄호에 반복 간 최소~최대를 적었다. 레이아웃은 12열, 3x2 항목을 4개씩 쌓은 빽빽한 배치이며 title/content/props 를 가진다.
* 화살표 앞의 값은 개선 전, 뒤의 굵은 값은 개선 후이다. 개선 전 수치는 같은 스크립트로 개선 전 코드에서 한 번 측정한 값이다(core 는 n=2000 을 시간 한도 때문에 측정하지 않았다).
* **이 수치는 프로그램 호출 경로의 비용이다. 사용자 드래그의 프레임 시간(포인터 이벤트 → 미리보기 → 페인트)이 아니다.** jsdom(Jest) 시간은 성능 지표로 쓰지 않았고 어떤 결과도 jsdom 수치로 해석하지 않았다.
* 노트북 환경이라 실행 간 편차가 크다(에디터 수치는 ±30% 이상 흔들릴 수 있음). 작은 차이(수 ms)는 의미가 없고 자릿수가 바뀐 변화만 유의하다고 본다.

## 2. 병목 분석

| 의심 항목 | 측정 결과 | 조치 |
| --- | --- | --- |
| 항목 수 증가에 따른 충돌 탐색 | `compact` 가 배치된 전체 항목을 선형 탐색 → n 에 대해 제곱 이상으로 증가 | 열별 색인(`ColumnIndex`)으로 같은 열의 항목만 탐색 |
| y 가 큰 항목을 한 행씩 올리는 압축 | `tall` n=1000 압축 **2.5초**, `moveItem` 3.0초 (y 가 클수록 선형 증가 × n) | 위로 올릴 위치를 한 번에 계산(`ceiling`), 충돌 시 아래로 점프 |
| 빈 자리 탐색 | `addItem` 자동 배치가 모든 (행, 열) 후보마다 전체 항목 선형 탐색 | 같은 색인 사용 + 막은 항목의 오른쪽 끝으로 건너뛰기 |
| 변경 없는 전체 항목 DOM 갱신 | `refresh` 가 n=1000 에서 약 1ms. 위치 문자열·콘텐츠 키 캐시가 이미 동작 | **조치 없음** (병목 아님) |
| 내부 이력을 끈 상태의 스냅샷 | 이력 스택은 이전 레이아웃의 **참조**만 쌓는다(항목 복사 없음). 이력 켬/끔 비교(워밍업 후 교대 6회, n=1000): 켬 22.1~26.7ms, 끔 22.4~26.4ms → **차이 없음** | 의미가 명확한 `history:false` 옵션 제공(메모리 보관 제거). 성능 개선 효과는 없음 |
| 이벤트용 복사 | `layoutChange` 마다 `cloneLayout`(n=1000 에서 약 0.8ms) + 변경 비교 | 리스너가 없으면(또는 `emit:false`) 복사·비교를 생략. 변경 감지를 JSON 직렬화 2회에서 구조 비교로 교체 |
| 외부 모델 동기화 시 반복 렌더링/이벤트 | 항목을 하나씩 `updateItem` 하면 항목마다 압축+렌더+이벤트 (n=1000, 20% 변경 시 이벤트 200회, 1916ms) | `syncItems()` 로 최종 상태를 한 번에 반영 (이벤트 1회, 18.8ms) |
| 위치 변경 시 브라우저 비용 | n=1000 의 `moveItem` 약 25ms 중 JS 구간(core 약 4ms + 직렬화/복사/applyItems 합 2ms 미만)을 뺀 나머지는 **속성 변경에 따른 스타일/레이아웃 계산**으로, 실제 위치가 바뀐 항목 수에 비례 | 변경된 항목만 DOM 에 쓰도록 이미 캐시됨. 추가 조치 없음 |

동일 입력의 배치 결과는 유지된다. `test/core/compactEquivalence.test.ts` 가 **개선 전 구현을 그대로 보존한 참조 구현**과 무작위 입력 3000건(겹침 입력, locked, anchor, float, 컬럼 4~12 조합)과 `findFreePosition` 2000건의 결과가 완전히 같음을 검사한다.

읽는 법
* `moveItem 변경 없음` 은 같은 자리로의 이동으로, 압축 계산과 변경 감지 비용이 드러난다.
* `syncItems` 와 `updateItem 개별 호출` 은 같은 변경(전체의 20% 항목의 폭을 번갈아 바꿈)을 반영하며 `layoutChange` 리스너 1개를 둔 상태이다. 이벤트 횟수는 n=100/300/1000 에서 1 대 20 / 1 대 60 / 1 대 200 이다.
* `생성(첫 렌더)` 가 개선 전보다 느려 보이는 것은 노이즈 범위이다(코드 경로가 같고 반복 간 편차가 같은 크기). 첫 렌더 비용은 DOM 요소 생성이 지배한다.

## 5. 남은 한계

* 압축 자체는 항목 수에 대해 여전히 대략 O(n²/컬럼 수) 이다(열별 목록을 선형 스캔). n=2000 의 `compact` 가 15~16ms 수준이라 현재 사용 범위에서는 충분하며, 더 큰 규모가 필요해질 때 열별 정렬 구조로 바꾸는 것을 검토한다.
* 드래그 중 미리보기는 셀이 바뀔 때만 core 를 다시 계산한다(`PointerController`). 포인터 이동 중의 프레임 시간은 이 문서에서 측정하지 않았다.
* `tall` 은 의도적으로 극단적인 입력이다. 일반적인 편집 상태는 `dense`/`mixed` 에 가깝다.

## 6. 재현

```bash
npm run build
npm run bench:core                       # Node, dist/core.js
npx vite --config vite.config.dev.mjs --port 5199 --host 127.0.0.1 &
npm run bench:editor                     # Chromium (BENCH_URL 로 서버 주소 지정)
```

환경 변수: `BENCH_SIZES`(예: `100,300,1000`), `BENCH_BUDGET_MS`, `BENCH_REPEAT`.

## 7. 여러 컨테이너 (DriftManager)

* 화살표 앞은 **위치 스타일시트 공유 전**(에디터마다 시트 1개), 뒤는 공유 후이다. 두 경우 모두 Manager/공통 끌어오기 코드는 같다.

* Manager 자체의 비용: 같은 50개를 `createDriftEditor` 로 직접 만들 때(234ms)와 `register` 로 만들 때(228ms)가 같았다(공유 전, 1회 측정). 생성 비용은 에디터 생성 경로가 결정한다.

| 컨테이너 수에 비해 생성 시간이 초선형으로 증가 (공유 전 10개 22ms → 50개 173ms) | 에디터마다 `adoptedStyleSheets` 에 시트를 하나씩 추가하면서 문서 전체 스타일이 매번 무효화된다. 같은 DOM 으로 시트만 50개 추가해도 64ms, 시트 없이 강제 레이아웃만 하면 3ms 였다 | 규칙 내용은 (컬럼 수, gap, rowHeight, 행 범위)로만 정해지므로 **같은 설정의 에디터가 시트 하나를 공유**(참조 수, `data-ddr-geo`). 설정이 다르면 별도 시트 |
| 에디터마다 붙는 document 리스너 | 기존에는 에디터 생성 시 외부 끌어오기용 리스너 5개(pointerdown/move/up/cancel, keydown)를 항상 붙였다(코드 확인. 기존 코드에서 측정하지는 않았다) | `setupDragIn` 원본이 있거나 세션이 진행 중일 때만 붙이도록 지연. 측정 결과 에디터당 1개 |
| 공통 팔레트 끌기의 대상 판정 | 포인터 이동마다 등록된 캔버스의 사각형을 읽는다(컨테이너 수에 비례). 50개에서도 이동 1회 상위 5% 1.4ms 이하 | 읽기(대상 판정)를 먼저 하고 쓰기(ghost 이동)를 뒤로 옮겨 이동마다 강제 레이아웃이 반복되지 않게 했다 |
| 복원 시 불필요한 렌더/이벤트 | 컨테이너마다 `load()` 1회(렌더 1회, `layoutChange` 1회) | 조치 없음 |

남은 한계: 생성은 여전히 컨테이너 수에 대해 선형보다 약간 크다(에디터마다 강제 레이아웃 1회와 ResizeObserver 1개). 컨테이너 수백 개 규모는 측정하지 않았다.

## 8. 컨테이너 간 이동 (crossContainerDrag / transferItem)

`e2e/multi-container-perf.spec.ts`(같은 스펙에 이동 항목을 추가)를 다른 테스트와 분리해 `--workers=1` 로 2회 실행했다. Playwright 1.64.1 Chromium(headless, 1280x900), 컨테이너당 10개 항목(12열), 각 값은 3회 측정의 중앙값이고 괄호는 두 실행의 값이다. 워밍업은 하지 않았다(첫 측정도 중앙값 계산에 포함).

* 항목 드래그 pointermove 는 원본 컨테이너의 항목 핸들을 잡고 화면 여러 곳(다른 컨테이너 위 포함)으로 60회 이동시킨 동기 처리 시간이다. 프레임 시간이나 실제 터치 지연이 아니다. 이동을 켜면 포인터 아래 캔버스 판정이 컨테이너 수에 비례해 늘어 50개에서 P95 가 0.5~0.8 → 2.6~2.7ms 가 되었다. 이 값은 pointermove 리스너의 동기 처리 시간뿐이며 스타일·레이아웃·페인트·합성과 다른 스크립트 비용을 포함하지 않으므로, 16ms 보다 작다는 것만으로 60fps 를 보장하지는 않는다.
* 구현 전 비교: 같은 날 같은 환경에서 기록한 §7 의 공유 시트 적용 후 값(50개: 생성 43~51, 편집 23~33, 복원 3.5~4.5, 제거 7.0~7.5, 팔레트 이동 P95 1.1~1.4)과 비교하면 생성·편집·복원·제거·팔레트 이동은 실행 간 편차(노트북, ±30% 이상) 범위 안이다. 같은 스크립트로 구현 직전 코드를 다시 측정하지는 않았다(그 시점의 코드가 커밋되어 있지 않다).
* 리소스(CDP): document 리스너는 컨테이너당 1개, 해제 후 0개로 이동 기능 추가 전과 같다(이동은 새 document 리스너를 만들지 않는다). `e2e/multi-container-resources.spec.ts` 에서 50개 등록 → 49회 이동(+연결 undo/redo) → 해제를 6회 반복한 결과 ResizeObserver 활성 50 → 0, 위치 시트 1 → 0, 남은 에디터 0, DOM nodes 39·jsEventListeners 16 으로 일정했다. GC 후 힙은 2,612,344 → 2,657,376 bytes(5회째)로 조금씩 늘었으며, 이 짧은 반복으로 누수 여부를 판정할 수 없다(retaining path 분석은 하지 않음).
* 측정하지 않은 것: 강제 동기 레이아웃 횟수(trace), 동일 셀 계산 횟수의 계측값(코드상 같은 셀·같은 revision 이면 계산을 건너뛴다), 실제 기기 터치 지연.

## 9. 재검증 지적 사항 대응 (2026-11-07)

[cross-container-retest-2026-11-07.md](cross-container-retest-2026-11-07.md) 에서 "50개 생성 44ms → 80ms, 같은 실행 대조 없음"과 "GC 후 힙 증가, retaining 분석 없음"을 지적했다. 측정 방법을 다음과 같이 바꿨다.

* `e2e/multi-container-perf.spec.ts`: 측정 전 워밍업 1회(버림 — **대조군 `createPlain(25)` 만** 실행한다. Manager 등록·이동·Undo 경로 전체를 데우는 것은 아니다), 개수마다 **5회 중앙값**(이전 3회). 같은 실행 안에서 Manager 없이 `createDriftEditor` 로 만드는 **대조군(createPlain)** 을 Manager 측정과 순서를 번갈아 잰다.
* `e2e/multi-container-resources.spec.ts`: 힙 총량 대신 CDP `Runtime.queryObjects` 로 GC 후 살아 있는 `DriftEditor`/`DriftManager` 인스턴스 수를 센다.

결과 (Playwright 1.64.1 Chromium headless, 1280x900, `--workers=1` 단독 실행 2회, ms)

| 컨테이너 | Manager `register` 생성 | 대조군 `createDriftEditor` 생성 | 편집 | 이동 커밋 | 연결 undo | 항목 pointermove P95 (이동 꺼짐 / 켜짐) |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1.9, 2.0 | 2.1, 2.0 | 1.7, 1.4 | - | - | 0.5/0.4, 0.6/0.6 |
| 5 | 6.7, 6.6 | 5.1, 6.8 | 3.3, 3.3 | 0.9, 1.1 | 0.9, 0.8 | 0.4/0.7, 0.5/0.8 |
| 10 | 11.2, 10.7 | 13.3, 9.5 | 8.2, 7.7 | 0.9, 0.9 | 0.8, 1.0 | 0.5/0.8, 0.4/0.6 |
| 25 | 34.9, 21.3 | 24.1, 25.0 | 16.6, 14.9 | 1.0, 0.9 | 1.0, 0.8 | 0.5/1.0, 0.4/0.8 |
| 50 | 55.3, 68.3 | 59.5, 55.5 | 34.1, 28.7 | 1.5, 1.3 | 0.9, 0.9 | 0.5/1.8, 0.7/2.3 |

* 같은 실행 안에서 Manager 생성과 대조군 생성은 서로 엇갈리며(50개: 55.3 vs 59.5, 68.3 vs 55.5) 차이가 실행 간 편차보다 작다. 이 대조군은 같은 실행 안의 Manager 유무 비교이며 **과거 코드와의 전후 대조 실험이 아니다.** 따라서 이전 보고의 44 → 80ms 차이가 모두 실행 간 편차라고 단정할 수는 없고, 이 측정으로는 "같은 실행에서 Manager 경로가 직접 생성보다 뚜렷이 느리지 않다"는 것까지만 말할 수 있다. 생성 비용 자체는 에디터 생성 경로(DOM, ResizeObserver, 첫 렌더)가 결정한다.
* 리소스: 50개 등록 → 49회 이동(+연결 undo/redo) → 해제를 6회 반복한 뒤 GC 후 살아 있는 `DriftEditor` 0개, `DriftManager` 는 반복 전 기준값(하네스 모듈 변수가 들고 있는 destroy 된 1개) 그대로였다. DOM nodes 39, jsEventListeners 16 으로 일정. 힙 총량은 2,592,484 → 2,622,004 bytes 로 조금 늘었다. 관찰한 것은 `DriftEditor`/`DriftManager` **인스턴스가 남지 않았다**는 사실까지이며, 이것으로 메모리 누수 전체가 없다고 확대하지 않는다(힙 증가분의 출처 — V8 내부, 개발 서버 클라이언트, 라이브러리의 다른 객체 — 와 retaining path 는 분석하지 않았다).

## 10. Sortable 결함 수정 후 재측정 (2026-11-08)

[SORTABLE_REMEDIATION_TASK.md](SORTABLE_REMEDIATION_TASK.md) 의 결함 A(콜백 안의 취소·해제 뒤 순서 변경)와 결함 B(관리할 수 없는 항목의 목록 간 이동)를 고친 **작업 트리**(기준 커밋 `44be542` + 미커밋 변경)에서 다시 쟀다. 위 §3~§9 의 표는 그대로 두고, 이 절은 별도 결과다. 측정 방법은 각 절과 같고 바꾸지 않았다.

환경: i7-8565U, win32 10.0.26200, Node v24.20.0, Playwright 1.64.1 Chromium 156.0.8078.4(headless, 1280x900). 기능 테스트(Jest, Playwright 전체)가 모두 끝난 뒤 `--workers=1` 로 측정끼리도 겹치지 않게 순서대로 실행했다. Editor 벤치는 이미 떠 있던 이 저장소의 Vite 개발 서버(5179, 현재 소스)를 사용했다.

| 검사 | 결과 |
| --- | --- |
| Sortable 3000개 + 무거운 항목 (`e2e/sortable-perf.spec.ts` ×3) | 시작 16.4 / 23.9 / 15.0ms, 이동 평균 1.61 / 1.83 / 1.83ms, P95 9.8 / 10.2 / 10.3ms, 최대 13.4 / 13.3 / 13.4ms |
| core (`scripts/bench-core.mjs`, 기본 `BENCH_BUDGET_MS` 20000) | 84개 조합 모두 측정, 시간 상한 초과·생략 0. 가장 느린 값 mixed n=2000 resizeItem 25.5ms |
| 단일 Editor n=1000 (`scripts/bench-editor.cjs` 전체 ×3, 중앙값과 범위) | 생성 78.4ms(75.5~84.7), moveItem 변경 있음 20.7ms(19.8~21.9), syncItems 14.9ms(14.3~16.5), 개별 updateItem 1497ms(1452~1507) |

* 결함 수정은 Sortable 의 콜백 경계 검사(상수 비용)와, 항목이 **다른 목록에 처음 들어갈 때** 도착 목록의 `draggable` 판정(세션 동안 목록별 1회, DOM 을 잠시 옮겨 판정)을 더한다. 3000개 성능 검사는 같은 목록 안의 이동이라 이 판정을 거치지 않는다. 위 값은 작업지시서의 직전 재검증 참고값(시작 17.2~33.6, 평균 1.60~1.68, P95 9.7~9.9, 최대 12.5~15.6ms)과 같은 범위다. 직전 값은 다른 실행이므로 전후 대조 실험은 아니다.
* pointermove 수치는 리스너의 동기 처리 시간이다. 페인트·합성·다른 스크립트 비용은 포함하지 않으므로 60fps 보장으로 읽지 않는다.
* GC 후 인스턴스 결과는 라이브러리 인스턴스가 남지 않았다는 관찰이다. 힙 총량 증가(약 30KB)의 출처는 분석하지 않았고, 메모리 누수 전체가 없다는 결론으로 확대하지 않는다.
* 자리 판정의 좌표 읽기 횟수(jsdom, `test/sortable/perf.test.ts`): n=100/1000/3000 에서 포인터가 항목 위면 4회 이하, 항목이 아닌 곳이면 nearestItem 이 끄는 항목을 뺀 전 항목을 읽어 약 n회다(O(n)). 호출 횟수의 계측이며 실제 시간이 아니다.
